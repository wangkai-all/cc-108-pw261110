# 跨库订单分析：筛选下推 + 分批键查询 vs 整表读取对照

两个**完全独立的本地 SQLite 数据库**（客户库 / 订单库）之上的跨库查询演示。
分析页通过选择字段、筛选条件和关联键，查出指定地区客户的订单汇总；
同时展示真实执行计划、每个源实际返回的行数 / 字节数，以及最终明细。

全部代码仅依赖 **Python 标准库 + 原生 HTML/CSS/JS**，无第三方运行时依赖。
页面上的每一个数字都来自真实查询，不存在任何预设或写死的演示数值。

## 快速开始

```bash
# 1. 生成两个独立源数据库（固定随机种子，可复现）
python3 -I seed_data.py

# 2. 启动服务
python3 -I app/server.py --port 8000
# 打开 http://127.0.0.1:8000

# 3. 跑测试（全部针对真实数据库，无 mock）
python3 -I -m unittest discover -s tests -t .
```

### 两个源是真正独立的数据库

- `data/customers_db.db` 与 `data/orders_db.db` 是两个独立磁盘文件、两条独立连接；
- 每次执行各源**单独打开只读事务固定快照**，并分别记录、展示快照时间；
- 系统**不存在也不声称存在跨库全局事务**。对照模式所说的“一致”，仅指
  两种方式在**同一组快照连接**读到的同一份数据上，应用层核对结果逐行相等。

## 两种执行方式

1. **键下推 + 分批（pushdown）**
   - 能在源端完成的筛选全部下推为带参数的 `WHERE`；
   - 先取符合条件的客户键（应用层去重、剔除 NULL），再按批次以 `IN (...)`
     查询订单，批次大小可在界面调整；
   - 没有符合条件的客户键时，**零明细请求**，绝不回退为查整张订单表；
   - 取消后在当前批次边界停止，**不再发出剩余批次请求**。
2. **整表读取对照（full_scan）**
   - 两表分别整表读回，用与下推 SQL 等价的 Python 谓词在应用层筛选，
     再走同一套哈希连接；
   - `compare` 模式在同一份快照上先后执行两种方式，逐行核对结果，
     并比较实际传回应用层的数据量（统一 UTF-8 JSON 字节口径）。

## 明确的连接 / 空值 / 重复键语义

内连接（`INNER JOIN ON customer_id`），全部边界情况显式计数，不静默丢弃：

| 情况 | 处理 |
|---|---|
| 客户键为 NULL | `NULL = NULL` 不为真，不参与连接，单独计数 |
| 订单键为 NULL | 不参与连接，单独计数（下推模式用源端 `COUNT` 补数，因为这些行不会传回） |
| 客户键重复 | 订单与每个匹配客户行各产一条明细（SQL JOIN 乘法）；`IN` 只发去重后的键 |
| 同一客户多笔订单 | 全部保留，不做任何“为少传数据”的预聚合或截断 |
| 孤儿订单（无匹配客户） | 内连接排除，但单独计数，不当作丢失 |
| 任一批次失败 | **整次执行失败**，失败批次不当空结果，不形成可下载结果 |

## 故障注入（界面可操作，均走真实查询路径）

- 按源注入语句延迟（ms）与语句超时（ms）：超时触发真实失败；
- 指定某源第几批注入失败：验证“失败即整体失败、不可下载”；
- 运行中取消：验证剩余批次请求确实不再发出；
- 切换地区：验证结果随真实查询变化，而非固定数字。

## REST API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/config` | 源、列、操作符、枚举等界面配置 |
| POST | `/api/runs` | 提交一次执行（后台运行），返回 `run_id` |
| GET | `/api/runs/{id}/status` | 轮询状态；completed 时含完整结果（不含可下载全量明细） |
| POST | `/api/runs/{id}/cancel` | 取消运行 |
| GET | `/api/runs/{id}/download` | 下载 CSV；**仅 completed 返回 200，其余 409** |

状态机：`running → completed | failed | cancelled`。
只有 `completed` 持有可下载的正式结果。
